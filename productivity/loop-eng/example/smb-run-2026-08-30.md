# Cold run — `smb-1`, 2026-08-30

The first end-to-end run of the loop on a ticket nobody had solved. Recorded
here as evidence the pipeline closes, and as a list of what it caught.

**Input:** `example/smb-client-server.md` — three vague lines, typo included.
**Artifacts:** `~/progress/smb-1/` (private, not in this repo).
**Code:** a throwaway target repo; PR opened, reviewed, and documented.
**Model:** Sonnet for every stage, on purpose — testing on the weaker model is
the only way a missing instruction shows up as a gap instead of being silently
inferred.

## Result

All six stages ran. Each in its own fresh session. None chained into the next.

| Stage | Outcome |
|---|---|
| `spec` | classified the ticket as a story (no `rca`), interviewed the operator, wrote 7 acceptance criteria |
| `impl` | blocked for seam confirmation, discovered no non-interactive sudo, redesigned rootless, committed code + tests |
| `verify` | 7/7 dev cases PASS, 5/5 E2E cases PASS, wrote the trace. No `fix-qa` loop needed |
| `pr-create` | no remote and no context file existed — asked, installed `gh`, created the repo, opened the PR |
| `pr-review` | security gate cleared empirically; three-axis review found two real defects |
| `kb-update` | wrote the architecture doc, created the repo's first `CLAUDE.md` with a pointer to it |

## What the loop caught that a single session would not have

`pr-review`, which never saw `impl` reason, found that the spec's claim of a
"dedicated local Samba user" was not literally true — the implementation
aliased an existing account. It also found an acceptance criterion tested only
half of what it claimed (bad password, never guest access).

Both are the same class of defect: the implementation drifted from the spec's
wording, and the session that wrote the code had rationalised the drift. Only
a session that had not been part of that reasoning saw it.

## What broke

Nothing in the contract. Every fallback that fired announced itself: no
project context file at `spec`, no control case at `verify` (first ticket in
the repo — substituted a base-environment check and said so), no configured PR
host at `pr-create`, no `rca.md` at `kb-update`.

The `verify` stage's insistence on a separate E2E pass earned its keep: the
dev tests exercised the client as a Python object, which is not what a user
does. The E2E pass drove the actual CLI as a subprocess and found the two
surfaces genuinely differ.

## Check F, same day

A session that had read only `SKILL.md` — not `SPEC.md`, not `reference/` —
was asked what it would have to guess to run `verify`. It named four things:
the ticket ID (not supplied), the progress root (correct — `SKILL.md` tells it
to read the personal context file, which it was not allowed to open), the
verify procedure, and the no-test-automation fallback. The last two live in
`reference/ticket-verify.md`, which it had been told not to read.

No gap in `SKILL.md` itself. The routing layer holds on its own.
